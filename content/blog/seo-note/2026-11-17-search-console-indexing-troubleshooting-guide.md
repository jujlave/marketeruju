<p>글을 발행했는데 구글에서 검색되지 않으면 제목이나 키워드부터 바꾸기 쉽습니다. 하지만 페이지를 아직 수집하지 못한 것인지, 수집했지만 색인하지 않은 것인지, 색인은 되었지만 원하는 검색어에서 노출되지 않는 것인지에 따라 대응은 달라져야 합니다.</p>

<p>이 글에서는 <strong>Search Console로 검색되지 않는 페이지를 점검하는 순서</strong>를 정리합니다. 콘텐츠를 수정하기 전에 현재 상태를 확인하고, 크롤링·색인·대표 URL 문제를 구분하는 것이 출발점입니다.</p>

<h2>검색 노출과 색인은 어떻게 다를까?</h2>

<p>크롤링은 검색엔진이 페이지에 접근해 내용을 수집하는 과정이고, 색인은 수집한 정보를 검색에 활용할 수 있도록 처리하는 과정입니다. 검색 노출은 색인된 페이지가 특정 검색 상황에서 결과로 제공되는 단계입니다. 페이지에 접근할 수 있다고 해서 색인이나 노출이 보장되지는 않습니다.</p>

<p>색인된 글도 경쟁 상황이나 검색 의도에 따라 원하는 검색어에서 찾기 어려울 수 있습니다. <code>site:</code> 검색은 참고용으로 활용할 수 있지만, 검색 결과에 없다는 사실만으로 미색인을 확정하지 않습니다. 특정 URL의 상태는 Search Console URL 검사로 확인하는 것이 좋습니다.</p>

<h2>1. URL 검사로 현재 상태를 확인한다</h2>

<p>해당 사이트를 관리하는 Search Console 속성에서 문제가 있는 글의 정확한 URL을 입력합니다. http와 https, 도메인, 경로, 슬래시가 다른 URL을 검사하고 있지는 않은지 먼저 확인합니다. 리다이렉트가 있다면 최종 도착 URL도 검사합니다.</p>

<ul>
  <li>Google에 등록되어 있는 URL인지 확인한다.</li>
  <li>페이지 색인 생성 상태와 표시된 사유를 확인한다.</li>
  <li>마지막 크롤링 시점과 페이지 가져오기 결과를 확인한다.</li>
  <li>사용자 선언 표준 URL과 Google 선택 표준 URL을 비교한다.</li>
</ul>

<p>URL 검사에 표시되는 기본 정보는 Google이 이전에 처리한 상태입니다. 현재 페이지가 달라졌다면 실제 URL 테스트로 접근 가능 여부를 추가 확인합니다. 실제 테스트가 통과해도 색인이 보장되거나 검색 순위까지 검증되는 것은 아닙니다.</p>

<h2>2. 미색인 사유에 따라 점검 범위를 나눈다</h2>

<h3>발견됨 - 현재 색인이 생성되지 않음</h3>
<p>Google이 URL을 알고 있지만 아직 크롤링하지 않은 상태입니다. 서버 접근에 문제가 없는지, 신규 페이지가 기존 콘텐츠에서 연결되어 있는지, 사이트맵에 포함되는지 확인합니다. 이 상태만으로 콘텐츠 품질 문제나 특정한 기술 오류를 단정하지 않습니다.</p>

<h3>크롤링됨 - 현재 색인이 생성되지 않음</h3>
<p>페이지를 수집했지만 아직 색인하지 않은 상태입니다. 다른 글과 내용이 지나치게 비슷하지 않은지, 실제로 읽을 본문이 충분히 제공되는지, 오류 안내가 정상 페이지처럼 반환되지는 않는지 살펴봅니다. 같은 상태라도 원인은 다를 수 있으므로 무조건 글자 수부터 늘리지 않습니다.</p>

<h3>중복 페이지 또는 적절한 표준 태그가 포함된 대체 페이지</h3>
<p>대표 URL이 아닌 중복 URL이 제외되는 것은 정상일 수 있습니다. 검색에 노출하려는 원본이 정상적으로 색인되어 있는지 먼저 확인합니다. 잘못된 URL이 대표로 선택됐다면 canonical, 내부 링크, 사이트맵이 같은 URL을 가리키는지 점검합니다.</p>

<p>사이트 전체에서 같은 문제가 반복되는지는 <a href="https://support.google.com/webmasters/answer/7440203?hl=ko" target="_blank" rel="noopener">페이지 색인 생성 보고서</a>로 확인할 수 있습니다. 모든 제외 URL을 색인시키기보다 검색에 필요한 중요 페이지부터 구분하는 것이 좋습니다.</p>

<h2>3. 접근 차단과 검색 제외 설정을 구분한다</h2>

<h3>robots.txt는 크롤링 접근을 제어한다</h3>
<p>robots.txt에 해당 경로를 차단하는 규칙이 있으면 Googlebot이 본문을 가져오지 못할 수 있습니다. 브라우저에서는 열려도 검색엔진 접근이 차단될 수 있으므로 규칙과 실제 URL 테스트 결과를 함께 확인합니다. 로그인 요구, 서버 오류, 보안 서비스 차단도 별도 점검 대상입니다.</p>

<h3>noindex는 색인 제외를 요청한다</h3>
<p><code>noindex</code>는 메타 태그나 HTTP 응답 헤더로 전달할 수 있습니다. 공개하려는 페이지에 개발 환경용 설정이 남아 있지는 않은지 확인합니다. 검색 제외가 의도된 관리자·개인정보 페이지라면 설정을 유지해야 합니다.</p>

<p>두 설정은 같은 기능이 아닙니다. Google이 noindex를 읽으려면 페이지를 크롤링할 수 있어야 하며, robots.txt 차단만으로 검색 결과에서 URL이 완전히 사라진다고 볼 수 없습니다. 구체적인 동작은 <a href="https://developers.google.com/search/docs/crawling-indexing/block-indexing" target="_blank" rel="noopener">Google의 noindex 안내</a>에서 확인할 수 있습니다.</p>

<h2>4. canonical과 내부 링크를 확인한다</h2>

<p>검색에 노출하려는 글의 canonical이 다른 글이나 카테고리를 가리키면 대표 URL 신호가 의도와 달라질 수 있습니다. 특히 템플릿을 복사하거나 사이트를 이전한 뒤에는 여러 글에 같은 canonical이 남아 있는지 확인합니다.</p>

<p>대표 URL은 정상적으로 열려야 하며 내부 링크와 사이트맵도 같은 주소를 사용해야 합니다. canonical은 대표 URL 선택 신호이므로 설정했다고 반드시 그대로 채택되지는 않습니다. 자세한 기준은 <a href="/blog/canonical-tag-seo-guide/">캐노니컬 태그 가이드</a>에서 확인할 수 있습니다.</p>

<p>신규 글이 사이트맵에만 있고 기존 글이나 목록에서 연결되지 않는지도 살펴봅니다. 연결을 보완하는 방법은 <a href="/blog/internal-link-blog-plp-guide/">내부 링크 설계 가이드</a>를 참고할 수 있습니다.</p>

<h2>5. 수정 후 다시 검사하고 변화를 기록한다</h2>

<p>문제를 수정했다면 실제 URL 테스트로 현재 접근 상태를 확인하고, 필요한 경우 색인 생성 요청을 진행합니다. 요청은 재처리를 알리는 방법이며 즉시 색인되도록 강제하는 기능이 아닙니다. 같은 URL에 요청을 반복하는 것보다 변경 내용과 확인 결과를 남기는 편이 운영에 도움이 됩니다.</p>

<ul>
  <li>수정한 URL과 최초 확인 사유를 기록한다.</li>
  <li>robots.txt, noindex, canonical 등 변경한 설정을 기록한다.</li>
  <li>수정일과 마지막 크롤링 시점의 선후 관계를 확인한다.</li>
  <li>이후 URL 검사에서 색인 상태와 선택된 대표 URL을 다시 확인한다.</li>
  <li>색인된 뒤에는 검색 실적 보고서에서 쿼리별 노출을 살펴본다.</li>
</ul>

<h2>검색되지 않을수록 상태 확인이 먼저다</h2>

<p>구글에 글이 보이지 않는 이유는 하나로 정해져 있지 않습니다. 미수집, 미색인, 의도된 중복 제외, 특정 검색어에서의 노출 부족을 구분해야 필요한 작업을 선택할 수 있습니다. 상태를 확인하지 않고 제목과 본문을 반복 수정하면 원인을 추적하기도 어려워집니다.</p>

<p><a href="/blog/seo-basic-checklist/">SEO 기본 체크리스트</a>와 함께 중요한 페이지의 접근 상태부터 점검해보세요. 색인 문제가 해결된 뒤 검색 의도와 콘텐츠 구성을 검토하면 기술 문제와 콘텐츠 개선 과제를 더 명확하게 나눌 수 있습니다.</p>
